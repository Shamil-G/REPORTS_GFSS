# REPORTS_GFSS

Flask-приложение отчётности АО «ГФСС». Формирует тяжёлые отчёты из Oracle в xlsx,
кладёт их на диск и не пересчитывает повторно, опираясь на реестр готовых отчётов
в БД.

Эталон для остальных модулей — [reports/DAUS/app_32.py](reports/DAUS/app_32.py).

Ключ отчёта в `reports` — **порядковый номер внутри группы** (`"01"`, `"02"`, …),
а не номер приложения. Первая цифра идёт на отображение, `view_extract_params`
разбирает её через `int()` + `zfill(2)` — то есть ключ обязан быть числом.
Номер приложения живёт в `report_code` (`APP.32`) и в названии; если положить его
ещё и в ключ, он попадёт в имя файла дважды (`32.APP.32`).

Форма запуска — два поля, оба выпадающими списками: `REP_YEAR` (годы вниз от
текущего, текущий по умолчанию) и `PERIOD` (20 конкретных периодов, значение
`"2.3"` = тип 2, номер 3). Отдельного поля «№ периода» быть не должно — номер без
типа пользователю ничего не говорит. Значение по умолчанию задаётся ключом
`"default"` в описании параметра; поддержка добавлена в `templates/edit_params.html`.

Значения, зависящие от даты (список годов, текущий месяц), нельзя вычислять при
импорте: `meta_params` живёт в `dict_reports` всё время работы процесса. Такие
поля помечаются ключом `"dynamic"`, подстановка — `resolve_dynamic()` в
`model/reports_info.py`.

## Имя файла и журнал отчётов

Имя файла собирает `call_report()` из отдела, группы, номера отчёта, `report_code`
и **всех непустых параметров формы**. Для отчётов с периодом код периода в имени
заменяется на человеческое название, поэтому запуски за разные периоды не
сталкиваются и файл читается глазами:

```
ДАУС.Приложения Минтруда.01.APP.32.2026.сентябрь.xlsx
ДАУС.Приложения Минтруда.01.APP.32.2026.II квартал.xlsx
```

Там же период разворачивается в `date_first` / `date_second` для
`LOAD_REPORT_STATUS`. Без этого в журнале готовых отчётов все запуски одного
отчёта — строки с одинаковым именем и пустыми датами, их не отличить. Блок
срабатывает только когда в параметрах есть и `rep_year`, и `period`, — на
остальные отчёты не влияет.

Повторный запуск с теми же параметрами даёт то же имя файла, `check_report()`
видит готовый файл и отдаёт его, не пересчитывая.

## Ловушка: порядок ключей в словарях

`meta_params` проходит через `session`, а сессия сериализуется в JSON. Flask по
умолчанию (`app.json.sort_keys = True`) сортирует ключи по алфавиту, и порядок,
заданный в `dict_reports`, терялся: поля формы шли `period` раньше `rep_year`,
годы — от 2005 к текущему, месяцы — «январь, октябрь, ноябрь, декабрь, февраль».
В `__init__.py` сортировка отключена. Не включать обратно: порядок словарей в
этом проекте несёт смысл — это порядок строк в выпадающих списках.

Два правила, которые задают вид всех переносимых запросов:

- **Границы периода полуоткрытые**: в SQL всегда `>= :d_from and < :d_to`.
  `between` и `trunc()` по дате не использовать — они блокируют индекс.
- **Итог по колонке среднего** считается из исходных сумм и количеств
  (`Col(kind='avg', avg_of=(...))`), а не сложением средних. Расхождение
  с эталоном в этой строке ожидаемо и согласовано 28.09.2026.
- **Подпись периода в заголовке** у каждого отчёта своя и задаётся в нём:
  `period_label=make_period_label({...})` с шаблонами из исходника дословно.
  Без него берутся формулировки приложения 32.

Перед переносом семейства — чек-лист «Порядок переноса одного семейства»
в плане: одиннадцать пунктов, каждый закрывает реально случившуюся ошибку.

Бинды объявлять не надо: `build_report` берёт параметры формы, добавляет
`d_from` / `d_to` / `y_from` и отдаёт в запрос только то, что реально упомянуто
в его тексте. Уровень отчёта (`lev` старого реестра) в описание не закладывается:
все отчёты пакета центральные, а областной разрез при необходимости делается
обычным параметром `rfbn_id`.

## Как устроено формирование отчёта

```
view/routes.py → model/call_report.py::call_report(dep, group, num, params)
   ├─ имя файла собирается из параметров → spool/<год>/<dep>.<grp>.<num>.<code>.<...>.xlsx
   ├─ check_report(file) → статус из LOAD_REPORT_STATUS
   │     0 нет файла · 1 готовится · 2 готов · 10 нет записи в журнале
   ├─ статус 1 или 2 → сразу вернуть путь, ничего не считая
   └─ иначе init_report() → reps.add_report() и запуск расчёта:
         unix    → subprocess: python -m report_runner <module_path> <json params>
         windows → loaded_module.thread_report(**params)
```

Модуль отчёта обязан предоставлять `do_report(**params)` и `thread_report(**params)`,
а также модульные константы `report_code` и `report_name`. `build_report()` возвращает
обе функции — при переносе их писать вручную не нужно.

Каталог отчётов — `dict_reports` в `model/list_reports.py`: отдел → группа → отчёт.
У группы задаются `module_dir` и `live_time` (часы жизни файла), у отчёта — `proc`
(имя модуля) и `meta_params` (описание полей веб-формы).

## Правила работы с БД

- Только через `db/connect.py`. Никаких `oracledb.connect` в модулях отчётов и
  никакого чтения `db_config.ini` — пул уже настроен.
- В отчётах использовать `select_2(stmt, params, profile=..., raise_on_error=True)`.
  `raise_on_error=True` обязателен: без него ошибка запроса вернёт пустой список,
  отчёт запишется пустым и получит статус «готов».
- Профили подключения: `DEFAULT_PROFILE` — схема `reports`, под ней работает
  приложение; `LOADER_PROFILE` — учётка загрузчика, нужна для боевых схем
  (`pnpd_document`, `pnpt_payment`, `person`, `si_member`), которые схеме `reports`
  не видны (иначе ORA-00942).
- Пул создаётся только после fork воркера (`post_worker_init` в `gunicorn.conf.py`),
  поэтому на уровне импорта модуля к БД не обращаться.
- Параметры — только именованные бинды (`:d_from`), никакой конкатенации значений
  в текст SQL.
- **Соединения — в старом синтаксисе Oracle**: таблицы через запятую в `FROM`,
  условия в `WHERE`, внешнее соединение через `(+)`. `JOIN` / `LEFT JOIN` / `ON`
  не использовать — ANSI-синтаксис раздувает код и читается хуже.
  `WITH`-подзапросы это правило не затрагивает, их используем свободно.

## Статусы отчёта

`set_status_report(file_path, status)` из `model/manage_reports.py`: `2` — готов,
`3` — ошибка. При ошибке битый файл нужно удалить, иначе он будет считаться готовым
результатом. `build_report()` делает это сам.

## Запуск

Windows, разработка:

```bash
python main_app.py
```

Поднимается на `localhost:5090` (см. `app_config.py`). `start.bat` делает то же,
предварительно активируя `venv`.

Linux, прод — gunicorn с `preload_app=True` и gevent-воркерами, конфигурация в
`gunicorn.conf.py`, точка входа `wsgi.py`.

## Стиль

Комментарии в коде и сообщения в логах — на русском, как в существующих модулях.
Тексты названий отчётов и заголовков колонок менять нельзя: это официальная
отчётность с согласованными формулировками.
