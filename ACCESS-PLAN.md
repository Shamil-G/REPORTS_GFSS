# План модернизации доступа: филиалы

Статус: черновик к обсуждению. Разбор — 15.10.2026, решения Шамиля по §9 внесены
15.10.2026. Ничего из описанного ещё не сделано.

## Постановка

До сих пор отчётность была «для избранных»: единственный отбор делался на входе
в систему — логинился только центральный аппарат, и дальше любой
аутентифицированный пользователь видел весь каталог. Теперь появляются филиалы,
а отчёт 6 («Обороты и назначения») с филиалами и работает в основном. Контроль
доступа при этом нужен **универсальный** — один механизм на все отчёты, а не
отдельная проверка внутри шестого.

## 1. Как устроено сейчас

**Субъект.** Живой путь авторизации один — SSO (`SSO_LOGIN = True` в
[gfss_parameter.py](gfss_parameter.py)); объект пользователя собирается в
[sso/sso_login.py](sso/sso_login.py) из ответа SSO-сервера: `post`, `dep_name`,
`ou_name`, `rfbn_id`, `fio`.

Роль выводится таблицами `admin_post` / `work_post` / `view_post`
([app_config.py:21](app_config.py:21)) — «должность → список департаментов»,
`'*'` = любой департамент. Результат:

- `self.roles` — **строка**, не множество ([sso/sso_login.py:12](sso/sso_login.py:12));
- `self.top_control` — 2 / 1 / 0, дублирует роль ([sso/sso_login.py:13](sso/sso_login.py:13));
- `self.rfbn_id` — филиал пользователя ([sso/sso_login.py:40](sso/sso_login.py:40)),
  **в приложении не используется нигде**, только пишется в лог;
- `self.ou_name` — короткое имя подразделения (атрибут `name` у OU, например
  `DITiTO`), тоже только в логе.

**Что реально приходит из SSO** (ответ на живой учётке, 15.10.2026, сокращён):

```json
{"user": {
    "login_name": "Гусейнов",
    "fio": "Гусейнов Шамиль Аладдинович",
    "post": "Главный разработчик",
    "rfbn_id": "0000",
    "dep_name": "Департамент информационных технологий и технического обеспечения",
    "dn": "OU=DITiTO,OU=002RS,DC=gfss,DC=kz",
    "principalName": "Гусейнов_Ш@gfss.kz",
    "ou_name": "DITiTO",
    "lagacy_name": "Центральный аппарат АО ГФСС",
    "subordinate_ou": [],
    "is_active": true
}}
```

Отсюда видно главное: **поля `roles` в ответе нет** — роль SSO пока не отдаёт
(см. § 3). `rfbn_id` приходит четырёхзначным, `ou_name` — коротким именем OU,
есть ещё не используемые `dn`, `subordinate_ou` (подчинённые подразделения — на
будущее, если понадобится доступ «руководитель видит свои отделы») и
`is_active`. `lagacy_name` (именно так, с опечаткой в SSO) совпадает с
`ldap_name` из [regions.py](regions.py).

**Чем сейчас отличаются роли.** Проверено грепом по всему приложению: `Operator`
и `Guest` не упоминаются **ни в одной проверке** — разница между ними ровно
нулевая. Работает только `Admin`, в двух местах ([view/routes.py:247](view/routes.py:247),
[templates/base.html:53](templates/base.html:53)). Третье состояние — «не попал
ни в одну таблицу должностей»: `init_user` возвращает `None`, и пользователь не
входит вовсе. То есть фактически роли сегодня дают два значения: `Admin` и
«обычный пользователь».

**Объект.** Отчёт о правах не знает ничего. Весь контроль доступа сегодня — это:

| Где | Что проверяется |
| --- | --- |
| [view/routes.py:247](view/routes.py:247) | `'Admin' in g.user.roles` — удаление отчёта из журнала |
| [templates/base.html:53](templates/base.html:53) | то же — показ пункта меню «Вспомогательные задачи» |
| [model/call_report.py:300](model/call_report.py:300) | `"audit": True` — журнал доступа для 6-1 / 6-2 |
| [util/person_access.py:20](util/person_access.py:20) | ИИН участника в Active Directory — отказ в данных сотрудников |

Последние две строки — это контроль **по человеку, о котором отчёт**, а не по
пользователю, который его запрашивает. Прав пользователя они не проверяют.

Остальные ~400 отчётов доступны любому, кто прошёл SSO.

**Мост «филиал ↔ код области» уже есть.** В [regions.py](regions.py) каждый код
несёт `legacy_name` и `ldap_name` («0100» → «Филиал по Акмолинской области»), а
`rfbn_id` того же вида приходит из SSO. Связывать подразделение с кодом области
заново не нужно.

**Мёртвые ветки.** [ldap/ldap_login.py](ldap/ldap_login.py),
[ldap/ldap_user_info.py](ldap/ldap_user_info.py) и каталог [db/](db) импортируют
`ldap_boss` из `app_config`, которого там нет, — то есть при `SSO_LOGIN = False`
приложение уже не поднимется. Правки прав вносить только в `sso/`; судьбу
`ldap/` и `db/` решить отдельно (выпилить или починить), но **не дублировать**
в них новую логику.

## 2. Принцип

Доступ описывается **признаками субъекта**, которые приходят из SSO, и ничем
больше. Признаков четыре:

| Признак | Что это | Пример значения |
| --- | --- | --- |
| `roles` | роль из SSO | `Admin` |
| `post` | должность | `Главный специалист` |
| `ou_name` | короткое имя подразделения | `DITiTO` |
| `rfbn_id` | филиал (код области) | `0000` — центр, `0100` — Акмола |

При этом `rfbn_id` отвечает не только за видимость, но и за **разрез данных**:
филиалу мало показать отчёт, ему нужно подставить его область в параметры и не
дать выбрать чужую. Для этого у признака есть особое значение `own` (§ 4).

Таблицы `admin_post` / `work_post` / `view_post` из `app_config.py` уходят:
должность перестаёт быть источником роли и становится обычным признаком, по
которому при необходимости можно отфильтровать конкретную группу отчётов.

## 3. Субъект: права, собранные при логине

**Источник роли — SSO** (решение от 15.10.2026). Роль приходит полем ответа
SSO-сервера, приложение её не вычисляет.

Признаки лежат прямо на объекте пользователя (`SSO_User`), отдельного класса
прав нет: четыре атрибута — `roles`, `post`, `ou_name`, `rfbn_id` — уже
выставляются в `init_user`, и `util/access.py` читает их по именам. Лишний слой
ничего бы не добавил.

Пустой `rfbn_id` считается не центром, а «неизвестно»: такой пользователь не
проходит ни один фильтр по области. Центральный аппарат — код, начинающийся
с `"00"`.

Требования:

- `roles` — множество; `'Admin' in g.user.roles` на строке работает как сравнение
  подстроки и при двух ролях соврёт;
- помощник обязан переживать анонимного пользователя (у `AnonymousUserMixin`
  нет `roles`): сейчас это держится на `{% if g.user.is_active %}` в шаблоне;
- `top_control` убрать — он повторяет роль третьим способом;
- починить [sso/sso_login.py:83](sso/sso_login.py:83): `self.roles.append(...)`
  на строке валит логин, если SSO вернёт ключ `roles`.

**Сколько ролей.** Сегодня работает одна — `Admin` (§ 1). Достаточно двух:
`Admin` и обычный пользователь. Третья (`Guest` — «только смотреть журнал, не
запускать») вводится, когда под неё появится хотя бы одна проверка; вводить её
заранее нечем наполнить.

**Роль SSO пока не отдаёт** — в ответе её нет (§ 1). Поэтому `init_user` берёт
роль из поля `roles`, если оно появится (строка или список), а до тех пор
выводит её по таблицам должностей, как раньше. Роли не нашлось ни там, ни там —
пользователь не входит, как и было.

**Согласовать с SSO-сервером:** имя и формат поля с ролями (ожидается список
строк) и набор значений. После этого этап 4 убирает переходный вывод и сами
таблицы должностей.

## 4. Объект: ключ `access` в `dict_reports`

По образцу ключа `"audit"` — он уже доказал, что схема работает. У группы и, при
необходимости, у отдельного отчёта (у отчёта переопределяет групповой):

```python
"access": {"roles": ["*"], "rfbn_id": "*"}          # пускаем всех
"access": {"rfbn_id": "0000"}                       # только центральный аппарат
"access": {"ou_name": "DITiTO"}                     # только ДИТиТО
"access": {"post": ["Директор"], "ou_name": "DAUS"} # директор ДАУС
"access": {"rfbn_id": "own"}                        # любой филиал, разрез - свой
```

Правила разбора:

- ключи — только четыре признака из § 2; значение — строка или список;
- `"*"` означает «этот признак не фильтрует» и равносилен отсутствию ключа;
- **несколько признаков — И** (должны совпасть все), **значения внутри одного
  признака — ИЛИ** (достаточно вхождения). Пример `{"post": ["*"], "ou_name":
  "DITiTO"}` читается как «должность любая И подразделение ДИТиТО»;
- сравнение точное; `ou_name` и `rfbn_id` — без учёта регистра и с обрезкой
  пробелов, так как это коды.

**Особое значение `"rfbn_id": "own"`** — не фильтр видимости, а разрез данных:
отчёт виден сотруднику любого филиала, но параметр `rfbn_id` ему подставляет
сервер (своя область), а в форме область не выбирается. Для центрального
аппарата `own` означает всю республику, то есть поле остаётся как сейчас.
Это тот случай, под который открывается группа 6.

**Значение по умолчанию** (согласовано 15.10.2026). Буквальное правило «наличие
признака начинает фильтровать» даёт обратное: группа без ключа `access` открыта
всем, то есть в день первого входа филиала ему достались бы все ~400 отчётов по
всей республике. Поэтому в [util/access.py](util/access.py):

```python
DEFAULT_ACCESS = {'rfbn_id': CENTRAL_RFBN}   # '0000'
```

Лежит рядом с самой проверкой, а не в реестре: `util/` не должен зависеть от
`model/`. Синтаксис при этом не меняется — где нужно открыть всем, пишем явно
`{"roles": ["*"], "rfbn_id": "*"}`. Сегодняшнее поведение сохраняется само
собой, филиалам группы открываются по одной и по согласованию.

**Опечатка в ключе закрывает группу.** `{"branch": "0000"}` — ключ не из
четырёх признаков, и такой `access` не пропускает никого. Если бы неизвестный
ключ просто игнорировался, опечатка открывала бы группу всем и это осталось бы
незамеченным; а так видно на первой же попытке.

**Область — первые два знака.** SSO отдаёт четырёхзначный код отделения
(`0100`), и область в нём — первые два знака; так же устроен
[regions.py](regions.py), а в реестре отчётов те же области записаны
двузначными (`01`, см. `LIST_REGION`). Поэтому обе стороны сравнения
приводятся к двум знакам: в `access` можно писать и `{"rfbn_id": "0100"}`, и
`{"rfbn_id": "01"}`, и `{"rfbn_id": "0000"}`, и `{"rfbn_id": "00"}` — разницы
нет. Пустое значение *параметра* отчёта при этом значит «вся республика»,
поэтому центральному аппарату `forced_rfbn` отдаёт пусто.

**Про признак `post`.** Должность приходит текстом, «Главный специалист» есть в
десятке департаментов, поэтому в одиночку он почти никогда не годится — только
вместе с `ou_name`. Плюс должности переименовывают: в `app_config.py` уже лежит
артефакт такого переименования (название департамента разорвано переносом
строки). Короткий `ou_name` устойчивее, `rfbn_id` — тем более.

**Проверить на живой учётке филиала**, что SSO действительно отдаёт для него
непустые `rfbn_id` и `ou_name` своего филиала. Весь разрез данных держится на
этом, а сейчас оба поля в приложении не используются и фактически не проверены.

## 5. Где проверять — три точки, больше нигде

1. **[model/reports_info.py](model/reports_info.py)** — `get_owner_reports` (25),
   `get_list_groups` (31), `get_list_reports` (44): отфильтровать по `access`.
   Это единственный источник меню, недоступное просто не показывается.
2. **[model/call_report.py:247](model/call_report.py:247)** — та же проверка ещё
   раз (меню скрыло, но `/extract-params/7` набирается руками) плюс
   подстановка `rfbn_id` для `"own"` — **до** сборки имени файла и до
   `init_report`.
3. **[view/routes.py](view/routes.py)** — журнал запусков и выдача файлов (см. § 6).

**Почему `rfbn_id` подставляет сервер, а не шаблон прячет поле.** `rfbn_id`
входит в имя файла ([model/call_report.py:308](model/call_report.py:308)), значит
у филиала А и филиала Б это разные файлы и реестр готовых отчётов их не
перепутает. Если же оставить поле в форме и только скрыть его в шаблоне, область
подменяется обычным POST-запросом.

**Ловушка в форме параметров.** `view_set_params` читает `request.form[parm]`
для каждого поля из `session['params']` — если поле `rfbn_id` просто не
отрисовать, будет `KeyError` и 400. Варианты: оставить поле списком из одного
значения (своего филиала) либо читать через `request.form.get` и подставлять
значение на сервере. Второе надёжнее.

## 7. Третий слой: доступ к данным по человеку

У 6-1 / 6-2 единственный параметр — `iin`, никакого `rfbn_id` там нет. Значит
`"rfbn_id": "own"` на них **не действует**: филиал введёт ИИН участника из
любого региона и получит данные.

Разрез для таких отчётов берётся из самих данных: в `check_person_access`
([util/person_access.py:20](util/person_access.py:20)) добавить сверку региона
участника (`person` / `si_member` → `rfbn_id`) с `rfbn_id` пользователя. Это
независимый слой — «можно ли смотреть именно этого человека», — и он не
смешивается с признаками доступа. Существующий хук `check_params` в
`build_report` для него правильное место: механизм уже есть, добавляется одно
условие.

Сюда же относится действующий запрет на данные сотрудников (ИИН в AD,
[util/ad_check.py](util/ad_check.py)) и журнал доступа
([util/access_audit.py](util/access_audit.py)) — они остаются как есть.

## 9. Вопросы

**Решено 15.10.2026:**

1. **Источник роли** — SSO.
2. **Сколько ролей** — хватает двух (`Admin` и обычный пользователь); `Guest`
   заводить, когда появится своя проверка. Разница между `Operator` и `Guest`
   сегодня нулевая (§ 1).
3. **Форма описания прав** — ключ `access` с признаками `roles` / `post` /
   `ou_name` / `rfbn_id`; наличие признака включает фильтрацию по вхождению (§ 4).
4. **Значение по умолчанию** для группы без `access` —
   `DEFAULT_ACCESS = {"rfbn_id": "0000"}`, только центральный аппарат.

**Открыто:**

5. **Что именно открывать филиалам** и в каком разрезе — список групп от
   Заказчика. До этого списка этап 5 не начинается.
6. **Видит ли филиал запуски соседнего филиала в журнале?** Предложение: нет,
   видит свои и республиканские; ЦА видит все.
7. **Межрегиональные случаи отчёта 6**: участник переехал, выплата назначена в
   одном филиале, обороты по другому. По какому региону решать доступ?
8. **Кому положен разрез по всей республике** помимо ЦА — служба внутреннего
   контроля, актуарии?

## 10. Вне рамок

- `ldap_password` открытым текстом в [app_config.py](app_config.py) — отдельная
  задача, здесь не трогаем.
- Перенос `REP_STAT_EXTEND` (см. [CLAUDE.md](CLAUDE.md)) идёт независимо; новым
  отчётам достаточно не задавать `access` — они попадут под `DEFAULT_ACCESS`.
