# План модернизации доступа: филиалы

Статус: черновик к обсуждению, 15.10.2026. Ничего из описанного ещё не сделано.

## Постановка

До сих пор отчётность была «для избранных»: единственный отбор делался на входе
в систему — логинился только центральный аппарат, и дальше любой
аутентифицированный пользователь видел весь каталог. Теперь появляются филиалы,
а отчёт 6 («Обороты и назначения») с филиалами и работает в основном. Контроль
доступа при этом нужен **универсальный** — один механизм на все отчёты, а не
отдельная проверка внутри шестого.

## 1. Как устроено сейчас

**Субъект.** Живой путь авторизации один — SSO (`SSO_LOGIN = True` в
[gfss_parameter.py](gfss_parameter.py)); объект пользователя собирается в
[sso/sso_login.py](sso/sso_login.py) из ответа SSO-сервера: `post`, `dep_name`,
`ou_name`, `rfbn_id`, `fio`.

Роль выводится таблицами `admin_post` / `work_post` / `view_post`
([app_config.py:21](app_config.py:21)) — «должность → список департаментов»,
`'*'` = любой департамент. Результат:

- `self.roles` — **строка**, не множество ([sso/sso_login.py:12](sso/sso_login.py:12));
- `self.top_control` — 2 / 1 / 0, дублирует роль ([sso/sso_login.py:13](sso/sso_login.py:13));
- `self.rfbn_id` — филиал пользователя ([sso/sso_login.py:40](sso/sso_login.py:40)),
  **в приложении не используется нигде**, только пишется в лог.

**Объект.** Отчёт о правах не знает ничего. Весь контроль доступа сегодня — это:

| Где | Что проверяется |
| --- | --- |
| [view/routes.py:247](view/routes.py:247) | `'Admin' in g.user.roles` — удаление отчёта из журнала |
| [templates/base.html:53](templates/base.html:53) | то же — показ пункта меню «Вспомогательные задачи» |
| [model/call_report.py:300](model/call_report.py:300) | `"audit": True` — журнал доступа для 6-1 / 6-2 |
| [util/person_access.py:20](util/person_access.py:20) | ИИН участника в Active Directory — отказ в данных сотрудников |

Последние две строки — это контроль **по человеку, о котором отчёт**, а не по
пользователю, который его запрашивает. Прав пользователя они не проверяют.

Остальные ~400 отчётов доступны любому, кто прошёл SSO.

**Мост «филиал ↔ код области» уже есть.** В [regions.py](regions.py) каждый код
несёт `legacy_name` и `ldap_name` («0100» → «Филиал по Акмолинской области»), а
`rfbn_id` того же вида приходит из SSO. Связывать AD-подразделение с кодом
области заново не нужно.

**Мёртвые ветки.** [ldap/ldap_login.py](ldap/ldap_login.py),
[ldap/ldap_user_info.py](ldap/ldap_user_info.py) и каталог [db/](db) импортируют
`ldap_boss` из `app_config`, которого там нет, — то есть при `SSO_LOGIN = False`
приложение уже не поднимется. Правки прав вносить только в `sso/`; судьбу
`ldap/` и `db/` решить отдельно (выпилить или починить), но **не дублировать**
в них новую логику.

## 2. Принцип: развести два измерения

Сегодня «роль» склеивает две независимые вещи. С филиалами их надо разделить —
это главное решение плана:

| | Что отвечает | Источник |
| --- | --- | --- |
| **Право** | что человеку можно: какие группы отчётов, удаление из журнала, загрузка МИНСО | роль (`Admin` / `Operator` / `Guest`) |
| **Разрез** | чьи данные он вправе видеть: вся республика или один филиал | `rfbn_id` субъекта |

Почему нельзя оставить как есть: оба измерения выводятся из `post` + `dep_name`,
и если добавить туда филиалы, таблицы в `app_config.py` станут справочником
«20 филиалов × должности», который правится релизом при каждом кадровом
движении. Разрез из должности выводить и не требуется — он уже приходит готовым
в `rfbn_id`.

## 3. Субъект: один объект прав, собранный при логине

Новый модуль `util/access.py`:

```python
class Rights:
    roles: set[str]      # {'Operator'} - множество, а не строка
    rfbn_id: str         # '0100'; '' или '0000' - центральный аппарат
    central: bool        # rfbn_id in ('', '0000')
```

Собирается один раз в `SSO_User.init_user`, кладётся на `g.user`. Требования:

- `roles` — множество; `'Admin' in g.user.roles` на строке работает как сравнение
  подстроки и при двух ролях соврёт;
- помощник обязан переживать анонимного пользователя (у `AnonymousUserMixin`
  нет `roles`): сейчас это держится на `{% if g.user.is_active %}` в шаблоне;
- `top_control` убрать — он повторяет роль третьим способом;
- починить [sso/sso_login.py:83](sso/sso_login.py:83): `self.roles.append(...)`
  на строке валит логин, если SSO вернёт ключ `roles`.

**Откуда брать роль.** Предложение: из группы Active Directory
(`GFSS-REPORTS-ADMIN` / `-OPERATOR` / `-GUEST`), атрибут `memberOf` уже
запрашивается ([ldap/ldap_user_info.py:56](ldap/ldap_user_info.py:56)). Тогда
права выдаёт ИТ или кадровик в AD без релиза, а таблицы должностей из
`app_config.py` постепенно уходят. Если SSO-сервер умеет отдавать `roles` сам —
брать оттуда, это дешевле. Решение нужно согласовать (см. открытые вопросы).

## 4. Объект: права декларативно в `dict_reports`

По образцу ключа `"audit"` — он уже доказал, что схема работает. У группы и, при
необходимости, у отдельного отчёта:

```python
"6 - Обороты и назначения": {
    "module_dir": f"{REPORT_MODULE_PATH}.DIA.6",
    "live_time": 0,
    "access": {"roles": ["Admin", "Operator"], "branch": "own"},
    "reports": { ... }
}
```

Словарь `access` — два ключа:

- `roles` — кому группа видна. У отчёта переопределяет групповое значение,
  иначе наследуется.
- `branch` — разрез данных, ровно три значения:

| Значение | Поведение |
| --- | --- |
| `central` | только центральный аппарат. **Значение по умолчанию**: все существующие группы переносятся без строчки `access` и без изменения прав |
| `own` | филиал отчёт видит, но `rfbn_id` подставляется сервером и в форме не выбирается |
| `any` | выбор любой области — ЦА, контролёры |

Дефолт `central` — то, что делает переход безопасным: сегодняшнее поведение
сохраняется само собой, филиалам группы открываются по одной и по согласованию.

**Почему `rfbn_id` подставляет сервер, а не шаблон прячет поле.** `rfbn_id`
входит в имя файла ([model/call_report.py:308](model/call_report.py:308)), значит
у филиала А и филиала Б это разные файлы и реестр готовых отчётов их не
перепутает. Если же оставить поле в форме и только скрыть его в шаблоне, область
подменяется обычным POST-запросом.

## 5. Где проверять — три точки, больше нигде

1. **[model/reports_info.py](model/reports_info.py)** — `get_owner_reports` (25),
   `get_list_groups` (31), `get_list_reports` (44): отфильтровать по правам.
   Это единственный источник меню, недоступное просто не показывается.
2. **[model/call_report.py:247](model/call_report.py:247)** — та же проверка ещё
   раз (меню скрыло, но `/extract-params/7` набирается руками) плюс
   принудительная подстановка `rfbn_id` для `branch: "own"` — **до** сборки
   имени файла и до `init_report`.
3. **[view/routes.py](view/routes.py)** — журнал запусков и выдача файлов (см. § 6).

**Ловушка в форме параметров.** `view_set_params` читает
`request.form[parm]` для каждого поля из `session['params']` — если поле
`rfbn_id` просто не отрисовать, будет `KeyError` и 400. Варианты: оставить
поле списком из одного значения (своего филиала) либо читать через
`request.form.get` и подставлять значение на сервере. Второе надёжнее.

## 6. Что филиалы вскроют в первый же день

Это не гипотезы: сейчас всё держится на том, что пользователи — только ЦА.

- [ ] **`/uploads/<path:full_path>` без `@login_required`**
      ([view/routes.py:227](view/routes.py:227)). Отдаёт любой готовый файл из
      `spool` любому, кто знает путь. Путь виден в журнале запусков.
- [ ] **Журнал показывает всем всё.** `list_reports_by_day`
      ([model/reports.py:115](model/reports.py:115)) и `list_reports_global`
      ([model/reports.py:89](model/reports.py:89)) фильтруют только по дате и
      названию. Филиал Акмолы увидит строки и ссылки на файлы Алматы.
- [ ] **В `LOAD_REPORT_STATUS` нет владельца.** `reps.add_report`
      ([plsql/reps.pck:26](plsql/reps.pck:26)) принимает `rfbn_id`, но не логин.
      Фильтровать журнал по филиалу можно уже сейчас — по `rfbn_id` строки, — но
      у республиканских отчётов и у отчётов без области он пуст, и «свои
      запуски» филиал не отличит. Нужны колонки `owner` (логин SSO) и
      `owner_rfbn` в таблице и в `add_report`.
- [ ] **Роль-строка** — см. § 3.

## 7. Третий слой: доступ к данным по человеку

У 6-1 / 6-2 единственный параметр — `iin`, никакого `rfbn_id` там нет. Значит
`branch: "own"` на них **не действует**: филиал введёт ИИН участника из любого
региона и получит данные.

Разрез для таких отчётов берётся из самих данных: в `check_person_access`
([util/person_access.py:20](util/person_access.py:20)) добавить сверку региона
участника (`person` / `si_member` → `rfbn_id`) с `rfbn_id` пользователя. Это
независимый слой — «можно ли смотреть именно этого человека», — и он не
смешивается с ролями. Существующий хук `check_params` в `build_report` для него
правильное место: механизм уже есть, добавляется одно условие.

Сюда же относится действующий запрет на данные сотрудников (ИИН в AD,
[util/ad_check.py](util/ad_check.py)) и журнал доступа
([util/access_audit.py](util/access_audit.py)) — они остаются как есть.

## 8. Порядок работ

Этапы идут так, чтобы ни один не менял прав работающим пользователям до
последнего.

**Этап 1. Каркас.**
- [ ] `util/access.py`: `Rights`, сбор субъекта, разбор ключа `access`,
      дефолт `{"roles": [все], "branch": "central"}` для групп без ключа.
- [ ] `SSO_User.init_user` отдаёт `Rights`; `roles` — множество; `top_control` убран.
- [ ] Готово, когда: права никому не изменились, в логине видно роль и филиал.

**Этап 2. Проверки.**
- [ ] Фильтрация меню в `model/reports_info.py`.
- [ ] Проверка прав и подстановка `rfbn_id` в `call_report` до сборки имени файла.
- [ ] `edit_params.html` / `view_set_params`: поле области для `branch: "own"`.
- [ ] Готово, когда: ЦА видит каталог как раньше, тестовая учётка филиала не
      видит ни одной группы (все ещё `central`).

**Этап 3. Журнал и файлы** (§ 6).
- [ ] `login_required` на `/uploads` + сверка филиала строки журнала.
- [ ] `owner`, `owner_rfbn` в `LOAD_REPORT_STATUS` и в `reps.add_report`.
- [ ] Фильтр журнала по филиалу; ЦА видит всё.

**Этап 4. Источник роли.**
- [ ] Роль из группы AD (или из SSO), таблицы должностей из `app_config.py` убрать.
- [ ] Решить судьбу мёртвых `ldap/` и `db/`.

**Этап 5. Открытие отчётов филиалам.**
- [ ] Группа 6 — первый кандидат на `branch: "own"`, вместе с § 7.
- [ ] Дальше — по одной группе, по согласованию с Заказчиком.

## 9. Открытые вопросы к обсуждению

1. **Источник роли** — AD-группы, SSO или таблица в схеме `reports` с экраном
   администрирования? Предложение: AD-группы (§ 3).
2. **Три роли или больше?** Сейчас `Admin` / `Operator` / `Guest`, причём
   `Guest` ни на что не влияет: отчёт он запускает так же, как `Operator`.
   Нужна ли роль «только смотреть журнал»?
3. **Что именно открывать филиалам** и в каком разрезе — список групп от
   Заказчика. До этого списка этап 5 не начинается.
4. **Видит ли филиал запуски соседнего филиала в журнале?** Предложение: нет,
   видит свои и республиканские; ЦА видит все.
5. **Межрегиональные случаи отчёта 6**: участник переехал, выплата назначена в
   одном филиале, обороты по другому. По какому региону решать доступ?
6. **Кто имеет право на разрез `any`** помимо ЦА — служба внутреннего контроля,
   актуарии?

## 10. Вне рамок

- `ldap_password` открытым текстом в [app_config.py](app_config.py) — отдельная
  задача, здесь не трогаем.
- Перенос `REP_STAT_EXTEND` (см. [CLAUDE.md](CLAUDE.md)) идёт независимо; новым
  отчётам достаточно не задавать `access` — они получат дефолт `central`.
